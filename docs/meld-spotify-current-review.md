## What runs where

Meld is an Android client, not a continuously hosted Spotify proxy or account service. The app hosts Spotify’s login page in its own WebView, captures `sp_dc` (and optional `sp_key`), and makes subsequent token and catalog requests from the app. The README describes Spotify as a data source and says Meld does not require Premium; its audio path is YouTube Music by default, with optional Qobuz. The reviewed source tree contains no Spotify backend deployment. A public static hash document on GitHub Pages and a scheduled GitHub Actions workflow are service-like dependencies, but they do not receive users’ Spotify credentials or proxy users’ Spotify requests.

The login screen clears cookies before a new login, intercepts the Spotify redirect, and starts token acquisition after cookie capture. `SpotifyAuth` fetches a public TOTP parameter from a GitHub Gist, fetches Spotify server time, generates the TOTP, and calls Spotify’s internal `/api/token` endpoint with the captured cookie. Later API calls send the bearer token directly to Spotify. The token endpoint, cookie exchange, TOTP mechanism, and Pathfinder persisted queries are private interfaces, not a supported Spotify API contract. See [`SpotifyLoginScreen.kt`](https://github.com/FrancescoGrazioso/Meld/blob/1ded7122ee0bd166bd703bfe3b63d233af8b7dcd/app/src/main/kotlin/com/metrolist/music/ui/screens/SpotifyLoginScreen.kt), [`SpotifyAuth.kt`](https://github.com/FrancescoGrazioso/Meld/blob/1ded7122ee0bd166bd703bfe3b63d233af8b7dcd/app/src/main/kotlin/com/metrolist/spotify/SpotifyAuth.kt), and [`Spotify.kt`](https://github.com/FrancescoGrazioso/Meld/blob/1ded7122ee0bd166bd703bfe3b63d233af8b7dcd/app/src/main/kotlin/com/metrolist/spotify/Spotify.kt).

## Registries and scheduled automation

There are two separate public data feeds:

| Feed | Maintainer and update path | Meld client behavior |
| --- | --- | --- |
| Spotify TOTP parameters (`s`, `v`) | The app points at a [community Gist](https://api.github.com/gists/22ed9c6ba463899e933427f7de1f0eef). The pinned Meld workflow tree contains no TOTP-generation or Gist-update workflow. | `SpotifyAuth.fetchNuance()` fetches the Gist when it needs a token. The Android implementation has no local TOTP-secret cache or last-good fallback. |
| Spotify GraphQL operation hashes | Meld’s `.github/workflows/spotify-hash-check.yml` runs at 06:00 UTC daily and can also be dispatched manually. The checker fetches Spotify’s web player bundle and lazy chunks, updates `docs/spotify-gql-hashes.json`, and the workflow commits the JSON and deploys `docs/` to GitHub Pages when the checkout differs. | `SpotifyHashSync` loads a cached registry on startup and fetches the live registry at startup; on `PersistedQueryNotFound`, the client tries a previous hash and asks for a forced registry refresh. Hardcoded hashes remain a fallback. |

The TOTP registry is therefore not a Meld-hosted authentication service. It is a public dependency operated separately from Meld. By contrast, the persisted-query registry is published from Meld’s own repository. The full pinned workflow list includes build, release, pull-request, title-prefix, and Spotify hash-check workflows, but no TOTP updater.

Two concrete maintenance issues appear in the pinned hash automation. First, the checker updates `last_verified` for every found operation and `last_updated` on every successful run, then writes the JSON even when no hash rotated. The workflow commits and deploys on any Git diff, so a normal successful daily run can produce a commit and Pages deployment each day despite the README/AGENTS description saying it commits when hashes change. Second, the workflow records the checker exit code but does not gate later steps on it: the command then runs `echo`, and the step also has `continue-on-error: true`; the saved output is not used. A fetch/parse failure can therefore leave a green workflow with a failure only in its log. See the pinned [`check_spotify_hashes.py`](https://github.com/FrancescoGrazioso/Meld/blob/1ded7122ee0bd166bd703bfe3b63d233af8b7dcd/.github/scripts/check_spotify_hashes.py) and [`spotify-hash-check.yml`](https://github.com/FrancescoGrazioso/Meld/blob/1ded7122ee0bd166bd703bfe3b63d233af8b7dcd/.github/workflows/spotify-hash-check.yml).

The workflow uses a standard `ubuntu-latest` runner in a public repository; GitHub documents standard hosted runners as free for public repositories. The material cost here is operational: unnecessary daily commits/deploys, noisy history, registry publication churn, and a repository token with `contents: write`, rather than an expected per-run runner bill. GitHub also warns scheduled events can be delayed or dropped during high load; the current 06:00 UTC schedule is exactly on the hour. [GitHub runner billing](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) · [Scheduled workflow limits](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Suggested fixes are small and measurable: update verification timestamps in a separate non-published status artifact, or only persist the hash JSON when its hash/status fields change; fail the workflow when the checker returns an error while treating its “updated” exit code as success; and move the cron away from minute zero. Keep the operation parser’s changes behind fixtures that verify the operation-to-hash association, because it infers mappings by nearby bundle text and chunk context.

## Session and token refresh

`SpotifyTokenManager` reads the access token and its expiry from DataStore. If the token is current, it installs it on the Spotify client. If expired, a process-wide mutex serializes refresh attempts and re-reads DataStore after acquiring the lock so a concurrent refresh can be reused. Refresh obtains the saved cookie and asks `SpotifyAuth` for a new token. On the specific error messages containing “anonymous” or “expired”, it removes the access token, expiry, and saved Spotify cookies and raises a re-login state. Other errors, including TOTP Gist or network failures, return `false` without clearing the saved cookie session. This makes retries possible, but error classification is based on message substrings rather than typed auth outcomes. See [`SpotifyTokenManager.kt`](https://github.com/FrancescoGrazioso/Meld/blob/1ded7122ee0bd166bd703bfe3b63d233af8b7dcd/app/src/main/kotlin/com/metrolist/music/utils/SpotifyTokenManager.kt).

`SpotifyHashSync` is client-side startup and rejection recovery, not an always-running daemon. `App.kt` loads the cached registry during startup and launches `sync()` on IO; that method fetches unconditionally. The class declares a 24-hour threshold and last-fetch key, but it does not implement the documented `syncIfStale` policy or read that timestamp. It loads the prior JSON from DataStore first and keeps hardcoded defaults if the registry is unavailable. A useful cleanup is either to implement the stated stale check or remove the unused threshold/key and update the comments. The README’s six-hour profile-data cache is separate from auth/hash refresh. See [`App.kt`](https://github.com/FrancescoGrazioso/Meld/blob/1ded7122ee0bd166bd703bfe3b63d233af8b7dcd/app/src/main/kotlin/com/metrolist/music/App.kt).

## Comparison with Burrata

Burrata keeps the same general separation between login and authenticated provider work, while making request scope and lifetime explicit in the companion and native worker. `extension/spotify-auth.js` validates the public TOTP registry, chooses the highest version, stores it in extension local storage for up to 24 hours, and uses a valid cached value if the registry is temporarily unavailable. The browser companion caches Spotify GraphQL hashes for 12 hours and can refresh once after a hash rejection. The native Spotify worker is one job per process, uses exact allowlisted URLs, bounds requests and the whole job, and relies on the app’s memory token coordinator for reusable access-token leases; a refresh within a new worker job fetches the TOTP feed again. See [extension auth](../extension/spotify-auth.js), [provider worker](../scripts/provider-session-worker.mjs), and [worker contract](provider-session-worker.md).

That makes the tradeoff clear: Meld’s Android process shares a mutex-protected token refresh and stores token/cookie material in DataStore; Burrata’s desktop path has OS-keyring confirmed credentials and explicit native worker bounds, while its browser extension caches last-good public registry data locally. Neither codebase should treat the TOTP Gist, Spotify’s web token route, or persisted-query hashes as stable provider APIs. Burrata’s existing docs correctly label its provider transport experimental and recommend failing closed when those feeds or endpoints change.
