Native startup and idle IPC qualification plan
Date: 2026-11-02

Purpose
- Compare the optimized Linux CI DEBs for baseline v0.1.26 and candidate
  v0.1.27. Use the exact downloaded CI artifacts, record their workflow run IDs
  and SHA-256 values, and keep their extracted payloads separate.
- The earlier manual DEBUG package is only a preflight; exclude it from startup
  timing and release comparisons. This plan has not collected optimized-package
  timing or idle IPC results.

Startup procedure
- Prepare the same synthetic 12-second fixture for each payload and use a
  private profile, isolated display, and virtual audio server. Do not use a
  normal Burrata profile or real media files.
- Run at least 20 measured first-track samples per 0/100 pending-quality-asset
  condition. The optional asset cohort uses 100 hash-valid hard links to one
  synthetic file with stale quality-facts hashes; it measures repeated hash
  verification and does not model 100 unique files or a slow disk.
- Interleave baseline/candidate runs and alternate build and condition order.
  Discard three warmups per build and condition. The startup gate binds first
  audio to the first track and playback generation, requires three seconds of
  playback before pausing, and validates captured stereo fixture PCM.
- After timing, perform one separate full two-track natural-completion capture
  per payload. Keep it out of startup medians. Do not flush global page cache or
  claim a cold OS cache, same-process warm restart, physical output, or final
  installed-package qualification.
- Compare the same build profile on both sides. Use optimized release-profile
  CI packages; diagnostic/debug packages are not comparable to release ones.

Optional idle IPC procedure
- Build the private WebKitGTK observer with
  `scripts/performance/ipc_counter_build.sh <private-dir>/libipc_counter.so`.
  The shim counts only the target Burrata process's Wry `::ipc` signal after
  successful registration. It records numeric counters only; it does not
  inspect payloads, commands, URLs, credentials, or audio.
- For each payload, launch a fresh private app process and counter file. After
  frontend readiness, discard three one-second warmup buckets, then read the
  local counter file for 20 measured one-second buckets without MCP calls in
  the sample loop. Require an attached observer before interpreting a count.
  Report per-bucket deltas/rates and the total delta/rate.
- The process uses an exec-in-place PID gate and a mode-0600 exclusive counter
  file. A missing file or `registered: 0` indicates instrumentation failure,
  not zero activity. MCP, plugin, and other IPC channels are outside this
  measurement.

Evidence boundary
- The runtime harness records only bounded Store connection-mutex counts,
  totals and maxima, plus an explicit `sqliteEngineBusyWait: not_measured`
  marker. `get_app_status` snapshots themselves contribute a small amount of
  lock activity. SQLite engine busy-handler wait is not measured.
- Keep raw monitor captures, private profiles, extracted payloads, and detailed
  logs in private evidence storage. Publish only concise sanitized summaries
  with artifact hashes, run IDs, sample counts, medians/p95 values, and scope.
- No optimized startup comparison, idle IPC window, package installation, or
  physical output qualification is claimed by this preparation document.
