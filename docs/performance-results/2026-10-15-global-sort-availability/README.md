# Global sort availability measurements

These are isolated **development-build Store microbenchmarks**, reading the first 200 Library records with source-order sorting. They exclude GUI rendering, playback, process CPU, and network. They are not release or whole-app performance qualification.

The all-known fixture can stop after a first-row probe. The sparse fixture deliberately lacks release date, BPM, key, plays and views, requiring proof of absence across the entire filtered relation. Missing fields must not be inferred from only the loaded page.

Each mode has three warmups. The three-read exploratory results are insufficient for percentile qualification; their reported p95 is the maximum sample. Full per-size median, p95 and worst results, paired legacy controls, and fixture labels are retained in the adjacent JSON files. Earlier failed and slower candidates are retained too.

The sparse regression remains unacceptable. The lazy-mask exploratory run completed: 50k sparse p95 is 3167.65 ms against a paired 165.27 ms legacy read. Profiling-enabled results include timing instrumentation overhead and remain a failed performance candidate. Typical 50k stage observations are approximately 1.86 seconds JSON parsing, 0.69 seconds row fetch/read and 0.10 seconds remaining mask checks; these are wall timings, not CPU-seconds. The adjacent stage-profile JSON retains all observations. This identifies full JSON hydration as the next optimization target. No candidate here establishes complete performance acceptance, and no public release has been made.

A separate selective-parser prototype was compiled outside the worktree with cached development dependencies and tested against the actual sort text/SQL helpers (11 standalone tests passed). In a parser-only synthetic 50k sparse Track scan, three measured wall times after three warmups had medians 2189.04 ms for full Value parsing and 1424.97 ms for selected paths. SQL and GUI were excluded. This is insufficient for the full Store target, so the larger visitor implementation remains an unapplied prototype. The next candidate is a compact database projection of only still-missing sort paths. See `selective-parser-only-exploratory.json` for scope and raw samples.

The compact SQLite projection was also tested with the actual `models::Track` serializer and sparse benchmark values (638-byte rows in struct declaration order). Three reads after three warmups measured 2103.52 ms median for full JSON read/decode and 1213.68 ms for compact path projection/decode. This excludes Store joins, asset preparation, count, presence reconstruction and GUI work. The earlier 642-byte manual-map and 195-byte minimal fixtures are superseded for performance judgment; the archived JSON distinguishes them. The projection patch remains unapplied. A persisted, correctly invalidated presence summary is under design because the streaming lower bound still exceeds the full-query target.

The isolated persisted-mask v9 candidate also remains below acceptance. Its actual Store sparse exploratory run used three warmups and three measured cycles for each size, resetting masks before every cold read. At 50k, cold Pending reads had median 865.59 ms / worst 1076.04 ms; warm Ready reads had median 959.31 ms / worst 1160.94 ms; the paired legacy read was 186.32 ms / 210.59 ms. Full bounded backfill (100 batches of 500) cost 11040.99 ms median / 13835.15 ms worst, excluding runtime yield delays. Pending is explicit and never an all-false answer, but this does not satisfy the read target. Three-sample p95 is only the maximum sample. The candidate is outside the worktree; no app migration occurred. `persisted-mask-cold-warm-exploratory-sparse.json` retains the per-size summary measurements; the original helper did not emit individual samples, so they cannot be recovered from this run. The next step is profiling the remaining aggregate cost and batch lock time, rather than promoting a warm-cache-only result.

A subsequent isolated exact-relation pending `EXISTS` probe returns before aggregation when any matching row is stale, and omits the empty asset-mask join for no-asset Ready reads. Three exploratory sparse samples now give 50k cold Pending median 161.22 ms / worst 162.10 ms (paired legacy 171.39 / 182.91 ms), while Ready remains above the 500 ms read target at 563.95 / 593.16 ms. Full backfill is 9791.31 / 10001.29 ms; the maximum single 500-row backfill-call wall time is 135.41 ms across measured cycles. These are test-only, unoptimized development measurements with stage profiling and query-plan output enabled. They exclude runtime yielding, GUI, CPU-seconds and release builds. Raw measured samples and stage observations are retained in `persisted-mask-shortcircuit-exploratory-sparse.json` and `persisted-mask-shortcircuit-stage-profile.json`. The observed 50k Ready aggregate itself costs roughly 335 ms plus a roughly 62 ms completion probe, identifying the aggregate as the next measured target. No candidate promotion occurred.

The next isolated candidate replaces ten SQL MAX/CASE aggregates with one registered bit-OR aggregate, retaining the exact-relation pending probe and a pending sentinel for unexpected null masks. All combined native regressions pass at the 696-test prototype checkpoint. Three sparse exploratory cycles now measure 50k cold Pending reads at median 159.66 ms / worst 167.95 ms, and Ready at 354.20 / 388.92 ms, against paired legacy 158.26 / 172.87 ms. Full backfill remains 9569.35 / 9632.59 ms; maximum 500-row batch wall time is 132.44 ms across measured cycles. These development microbenchmarks satisfy the numerical read bound in this small sample but do not establish p95 qualification, release or whole-app performance. All-known metadata and asset-backed datasets remain to measure; the latter still use dynamic per-request hydration. `persisted-mask-or-exploratory-sparse.json` retains raw samples and explicit scope. No candidate has been promoted.

The paired all-known exploratory run also completed: 50k cold Pending median 175.61 ms / worst 178.54 ms, and Ready 362.95 / 370.30 ms, against legacy 159.38 / 173.16 ms. This confirms the numerical 500 ms bound in three development samples for both no-asset fixtures, while exposing the remaining aggregate overhead versus the legacy read and earlier all-known fast path. It is not a twenty-sample p95 result. `persisted-mask-or-exploratory-known.json` retains the raw samples and separate backfill costs. Asset-backed reads must be measured before deciding whether to land the availability/runtime candidate.
