# Extractor reuse feasibility and matched diagnostics

This was a bounded public diagnostic run, not a playback-speed claim. The machine-readable redacted rows are in [`result.json`](./result.json), with the one-attempt Python dependency diagnosis in [`python-diagnostic.json`](./python-diagnostic.json); the harness is [extractor_reuse_experiment.py](../../../scripts/performance/extractor_reuse_experiment.py).

The runtime source matches the shipped yt-dlp pin: version `2026.10.10.233141`, full source commit `897341241f2bfb2439fe0367f4c7c9ccd29a3828`, release archive SHA-256 `f983c6d3ded7148de5b8b22a7db41e12cef05f38f1b5396985d969593efad059`. The bundled CLI SHA-256 is `60606cef1a65d70f6639a85b45ebb7acf08dbb81831e134dd93939e23ca2b792`. The local exact-source experiment used Python 3.14.8, whereas the frozen CLI has its own bundled runtime and dependency graph; therefore the two paths are not runtime-parity comparisons. A single bundled BgUtils helper was warmed and shared, and each attempt used a private one-use loopback gate/token. The run used no account, cookies, or user configuration.

There were three attempts for each arm in fixed order (bundled CLI, fresh Python worker/object, resident Python worker/object) over public diagnostic clips `jNQXAC9IVRw`, `BaW_jenozKc`, and `aqz-KE-bpKQ`. Each arm had a 20-second wall limit. The first resident attempt included worker spawn and readiness in that limit. Helper startup was shared setup and excluded from per-attempt timing; it took about 1.38 seconds. The order was not randomized, and provider/helper cache warming may have favored later arms.

The bundled CLI matched the requested identity and produced exactly five seconds of stereo 48 kHz signed-16-bit PCM in 2/3 attempts. Its median extractor process time was 4.45 seconds; median PCM completion time was 1.83 seconds. One clip failed extraction. The CLI process-time measure ends at metadata/URL resolution and excludes PCM probing.

Both exact-source Python arms failed before identity/format/PCM validation in all three attempts. Their medians, 2.89 seconds (fresh) and 2.28 seconds (resident), are time-to-failure only and cannot be interpreted as startup or playback improvements. The harness intentionally records only a safe generic error class, so these rows do not establish whether the failure was in Python setup/plugin loading, the provider response, or another extractor stage. The Python arm also used a CLI-side approximation of the selector while the embedded path used yt-dlp's selector implementation; successful format parity was not established.

An offline dependency check found that yt-dlp source expects the optional `yt-dlp-ejs` package at version `0.8.0`, matching the pinned source's EJS vendor version, but Python `-S` hid installed packages. A follow-up single attempt copied only that package into scratch, checked its minified solver hashes against the pinned source's allowlist, and succeeded for `jNQXAC9IVRw`: identity matched and five seconds of PCM were produced in about 4.94 seconds of extraction plus 0.40 seconds to complete PCM. This is a diagnostic follow-up, not a replacement for the original three-per-arm matrix. Its embedded selector returned format `18` while the CLI selected `140`, so the two paths still do not have established format parity.

The supported conclusion is limited: the pinned bundled CLI can produce usable audio for two of three tested public clips under this helper setup, and the exact-source Python path can work when its matching EJS dependency is supplied. This does not establish reusable-worker benefit, account behavior, queue gaplessness, or preview-path equivalence. A valid paired fresh/resident comparison still needs isolated matching dependency setup, identical selected format IDs, and separate startup, extraction, first-PCM, and five-second-PCM completion measures.

## Corrected same-ID and same-itag benchmark

Later work added the diagnostic-only `--matched` mode to the harness. It pins official Matthew upload `uZGRATckoBM`, mweb and itag `251` without format fallback. Only the extractor-selected top-level ID/format may reach decode. The fresh/resident Python paths use the same pinned source and hash-verified EJS package under `python -S`; bundled CLI retains a different frozen runtime/dependency graph. All arms use identical format/client request settings, the same allowlisted-header policy and the same FFmpeg decoder function. These controls do not make signed URLs or CDN behavior identical.

The parent measures each request through first PCM on the same host monotonic clock, including worker readiness when needed. Decoder-first-PCM and five-second completion are recorded separately. The warm shared helper's setup is excluded and reported. Three Latin-rotated blocks use CLI/fresh/resident, fresh/resident/CLI and resident/CLI/fresh ordering. Per-attempt wall budget is 20 seconds, total run budget 240 seconds, resident idle timeout 60 seconds. Reports retain typed failures and reject mismatched identity, format or stream fingerprints from paired deltas. The mode refuses to overwrite prior output files.

The [first matched matrix](./matched-matthew-251.json) preserves a harness error: unsupported `--no-netrc` caused the three CLI commands to exit before provider extraction. The raw safe category was `EXTRACTOR_ERROR`; a later offline complete-option check identified the usage failure. `--version` had returned before unknown-option validation. The command now omits the unsupported option (netrc is opt-in and config is ignored), emits `CLI_USAGE_ERROR` for future usage failures, and validates the full configured option set with network-free `--list-extractors`. That original matrix has one fresh-Python and one resident-Python success in different blocks, so neither planned comparison has a valid successful pair.

The [corrected-command matrix](./matched-matthew-251-cli-fixed.json) completed all nine attempts in 63.98 seconds, excluding 2.73 seconds of shared-helper setup. It has **one success in three attempts for every arm**:

| Block | Bundled CLI | Fresh Python | Resident Python |
| --- | --- | --- | --- |
| 1 | First PCM 8,893 ms; five seconds decoded | `STREAM_DENIED` | First PCM 6,027 ms; five seconds decoded |
| 2 | `FORMAT_UNAVAILABLE` | First PCM 7,083 ms; five seconds decoded | `STREAM_DENIED` |
| 3 | `STREAM_DENIED` | `STREAM_DENIED` | `STREAM_DENIED` |

All successful selections have equal source/format fingerprints: requested ID, itag 251, Opus/WebM, HTTPS, stereo 48 kHz and content length 3,845,541. No planned CLI/fresh-Python or fresh/resident-Python comparison has both successful rows within a block; every paired delta is therefore excluded. CLI and resident both succeeded in block 1, but the resident was on its first object use and their runtime graphs differ, so that observation does not isolate object reuse. Do not subtract successes from different blocks or turn failure time into a startup improvement.

The corrected run's script SHA-256 is `c839902e50a989569b8ea04bce70a8cf029e86721983e66b44a32fd0e90e213f`; the exact source-tree manifest and EJS hashes are retained in its assets. It reports no timeout, observed helper shutdown and `qualification:false`; complete CPU/RSS and mixer/device timing are outside this benchmark. The cause of individual format omissions/CDN denials is not established. Python reuse remains unqualified, and no more Python live matrices are planned without a concrete provider/access fix.

## More promising direct-worker feasibility

The separate [anonymous sequential direct-worker report](../../../scripts/performance/innertube/results/2026-10-19-matthew-same-worker-reuse.json) decoded all three five-second excerpts: first Matthew/itag 251 at 9,728 ms to first PCM, same Matthew/itag 251 again at 372 ms with token/info cache hits, and a different public video/itag 140 at 546 ms with fresh extraction and a new video-bound GVS token. These timers begin at request-line receipt and exclude process launch. This is one warm sequence, not a controlled Python/CLI comparison, full recording identity proof, full-song/device playback or statistical qualification.

The primary next direction is a persistent direct InnerTube worker with correct player/GVS binding, owned cancellation/idle/session lifecycle, production recording/version proof, expiry-aware native-source handoff and yt-dlp fallback. The observed warm values justify that targeted work; they do not qualify production promotion. The [research report](../../playback-startup-research.md) records source pins, all retained failures, missing steps and safety boundaries.
