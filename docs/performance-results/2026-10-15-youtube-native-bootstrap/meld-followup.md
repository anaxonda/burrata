This source review is pinned to [Meld `e0af26953c315e6d8dfcef25b6436f7747fb34c6`](https://github.com/FrancescoGrazioso/Meld/tree/e0af26953c315e6d8dfcef25b6436f7747fb34c6). It uses the four source snapshots supplied at `/tmp/MeldLoginScreen.kt`, `/tmp/MeldInnerTube.kt`, `/tmp/MeldYouTube.kt`, and `/tmp/MeldYouTubeClient.kt`, plus the corresponding pinned repository paths linked below. No account or cookie values were accessed.

## What Meld transfers from login

Meld opens the Music login flow in an Android WebView (or `music.youtube.com` directly for channel switching). After the page finishes on the Music origin, it polls up to 20 times: `CookieManager.getCookie("https://music.youtube.com")` gives the page's **whole cookie header**, while JavaScript reads `window.yt.config_.VISITOR_DATA`, `DATASYNC_ID`, and `SESSION_INDEX`. It requires `SAPISID` in the cookie map and visitor data; it stores the entire cookie string, visitor data, the first part of dataSyncId (before `||`), and numeric authUser. Source: pinned [`LoginScreen.kt`](https://github.com/FrancescoGrazioso/Meld/blob/e0af26953c315e6d8dfcef25b6436f7747fb34c6/app/src/main/kotlin/com/metrolist/music/ui/screens/LoginScreen.kt) (extraction around `extractAuthData`, persistence in `finalizeLogin`).

Before persistence it installs those four values into the native `YouTube` client and calls `accountsList()` to offer channel selection when multiple identities are returned. It uses the selected account's sign-in URL to switch, then re-reads the page config and overrides dataSyncId with the selected channel's sync ID. It calls `accountInfo()` after selection and saves account name, email, and channel handle alongside cookie/context. It clears WebView history/cache/form data, flushes cookies, and restarts the app process. The code does not show a normal-success-path `WebView.destroy()` or clearing of the WebView cookie jar. Same pinned [`LoginScreen.kt`](https://github.com/FrancescoGrazioso/Meld/blob/e0af26953c315e6d8dfcef25b6436f7747fb34c6/app/src/main/kotlin/com/metrolist/music/ui/screens/LoginScreen.kt).

This means Meld's transfer is not just three authentication cookie values. It passes the complete CookieManager header plus visitorData, selected dataSyncId, and authUser to its native client. The extra values affect request context/identity; they are not substitutes for the cookie.

## Native request and identity flow

Meld's local `InnerTube` facade constructs a Ktor/OkHttp client, then delegates API request construction, session management, retry behavior, and authenticated mutations to `com.metrolist.innertubex.InnerTube`. It proxies cookie, visitorData, dataSyncId, authUser, locale, and browse-login preference. The YouTube adapter invokes `account/accounts_list` for channel switching using WEB and `account/account_menu` with WEB_REMIX for account info; it reads the first active-account header's name/email/channel handle. Pinned [`InnerTube.kt`](https://github.com/FrancescoGrazioso/Meld/blob/e0af26953c315e6d8dfcef25b6436f7747fb34c6/innertube/src/main/kotlin/com/metrolist/innertube/InnerTube.kt) and [`YouTube.kt`](https://github.com/FrancescoGrazioso/Meld/blob/e0af26953c315e6d8dfcef25b6436f7747fb34c6/innertube/src/main/kotlin/com/metrolist/innertube/YouTube.kt).

The facade's default client uses `https://music.youtube.com/youtubei/v1/`, JSON negotiation, gzip/deflate, a 10-connection OkHttp pool, 30-second connect and 60-second read/write/request timeouts, connection retry, and a 50 MiB HTTP cache. This is client transport configuration, not proof that YouTube accepts all authenticated calls or that these private endpoints are stable. Source: pinned [`InnerTube.kt`](https://github.com/FrancescoGrazioso/Meld/blob/e0af26953c315e6d8dfcef25b6436f7747fb34c6/innertube/src/main/kotlin/com/metrolist/innertube/InnerTube.kt).

The client type is a typealias to InnerTubeX's `YouTubeClient`, so its numeric client IDs and context definitions come from that library: pinned [`YouTubeClient.kt`](https://github.com/FrancescoGrazioso/Meld/blob/e0af26953c315e6d8dfcef25b6436f7747fb34c6/innertube/src/main/kotlin/com/metrolist/innertube/models/YouTubeClient.kt) (the supplied snapshot is `MeldYouTubeClient.kt`, containing the alias).

## Dependency source boundary

The exact pinned Meld catalog resolves InnerTubeX as `com.github.MetrolistGroup.innertubex:innertubex` at **`v0.5.2`** ([pinned version catalog](https://github.com/FrancescoGrazioso/Meld/blob/e0af26953c315e6d8dfcef25b6436f7747fb34c6/gradle/libs.versions.toml), [pinned module dependency](https://github.com/FrancescoGrazioso/Meld/blob/e0af26953c315e6d8dfcef25b6436f7747fb34c6/innertube/build.gradle.kts)). I fetched the public [`v0.5.2` InnerTube implementation](https://github.com/MetrolistGroup/innertubex/blob/v0.5.2/src/commonMain/kotlin/com/metrolist/innertubex/InnerTube.kt) and its [`YouTubeClient` context builder](https://github.com/MetrolistGroup/innertubex/blob/v0.5.2/src/commonMain/kotlin/com/metrolist/innertubex/models/YouTubeClient.kt).

At v0.5.2 `sanitizeCookieString` strips CR/LF/tab, rejects other control characters, trims whitespace and an optional leading `Cookie:` prefix; it does not impose a cookie-name allowlist. The client then selects one proof input in this order: `SAPISID`, `__Secure-3PAPISID`, `__Secure-1PAPISID`. The SHA-1 input is `<unix-seconds> <selected-cookie-value> <request-origin>`; `Authorization` is `SAPISIDHASH <unix-seconds>_<lowercase-hex-digest>`. There is no extra digest suffix and the library does not emit separate `SAPISID1PHASH`/`SAPISID3PHASH` values. For Music (`WEB_REMIX`), the origin in the proof is `https://music.youtube.com`. The supplied cookie header (with locale `PREF` injected/replaced) is sent for login-supported clients; `X-Goog-AuthUser` and `Authorization` are added when the call opts into login and has a cookie. `X-Goog-Visitor-Id` is sent separately. Source: pinned dependency [`InnerTube.kt`](https://github.com/MetrolistGroup/innertubex/blob/v0.5.2/src/commonMain/kotlin/com/metrolist/innertubex/InnerTube.kt#L346), [`client header builder`](https://github.com/MetrolistGroup/innertubex/blob/v0.5.2/src/commonMain/kotlin/com/metrolist/innertubex/InnerTube.kt#L362), and [`cookie normalizer`](https://github.com/MetrolistGroup/innertubex/blob/v0.5.2/src/commonMain/kotlin/com/metrolist/innertubex/utils/Utils.kt#L3).

The identity split is explicit in v0.5.2: `authUser` becomes `X-Goog-AuthUser`; `dataSyncId` becomes `context.user.onBehalfOfUser` only for login-supported clients. Meld's facade calls `accountsList(YouTubeClient.WEB)`, so channel discovery uses WEB (`clientId` 1, pinned version `2.20260708.00.00`), WWW endpoint/origin/referer, and null dataSyncId in context. Separately, its `accountInfo()` calls `accountMenu(WEB_REMIX)`, which uses Music origin and includes dataSyncId. Both calls opt into login and carry cookie/auth headers. See Meld's pinned `/tmp/MeldInnerTube.kt:263`, `/tmp/MeldYouTube.kt:3200-3216`, InnerTubeX's [`toContext`](https://github.com/MetrolistGroup/innertubex/blob/v0.5.2/src/commonMain/kotlin/com/metrolist/innertubex/models/YouTubeClient.kt#L35), and [`accountMenu` and `accountsList`](https://github.com/MetrolistGroup/innertubex/blob/v0.5.2/src/commonMain/kotlin/com/metrolist/innertubex/InnerTube.kt#L1035). Generic requests attach cookies to login-supported clients by default, but only attach `X-Goog-AuthUser`/proof when `setLogin` is true (or the browse-login preference enables it); this explains why cookie presence alone is not the same as an explicitly authenticated call.

The default request helper retries transient status codes 408, 425, 429, 500, 502, 503, and 504, plus thrown exceptions, up to three attempts with 500 ms initial delay doubled each time. Mutations disable transient retries. Source: pinned dependency [`executeRequest`](https://github.com/MetrolistGroup/innertubex/blob/v0.5.2/src/commonMain/kotlin/com/metrolist/innertubex/InnerTube.kt#L452).

## Concrete comparison with Burrata's current native path

Burrata's native login collector whitelists 15 named YouTube/Google cookies, but its authorization proof inputs are restricted to the three `SAPISID`, `__Secure-1PAPISID`, and `__Secure-3PAPISID` variants, and at least one of those must be present. The worker validates the handoff, computes only their matching hash schemes, requires the exact allowlisted handoff cookie header on requests, and rejects unapproved origins/routes; see [collector validation](../../../src-tauri/src/managed_provider_session.rs), [`youtube-session-worker.mjs`](../../../scripts/youtube-session-worker.mjs), and the browser-side native client [`youtube-session-provider.js`](../../../extension/youtube-session-provider.js). Meld's inspected login code instead hands off the full Music-origin CookieManager string without an app-side cookie-name allowlist in the inspected login code. This is a meaningful credential-scope difference; it does not establish that copying Meld's broader cookie transfer is needed or appropriate for Burrata.

Burrata's channel-discovery request now mirrors Meld's distinct account-list route: fixed WEB client/version on `https://www.youtube.com`, with the proof recomputed against the WWW origin, while `account_menu` and subsequent Music requests retain the Music client/origin. The worker permits that single cross-origin endpoint only, binds Origin/X-Origin/Referer and the WEB identity to the fixed route, and continues to require the exact cookie handoff and omit `onBehalfOfUser` from the list. This is a source-matched compatibility candidate, not live qualification; the API key remains sourced from the Music bootstrap config.

Both implementations carry visitorData and authUser into authenticated InnerTube requests. Meld captures those values and dataSyncId from the logged-in Music page's `window.yt.config_` and substitutes the selected account's dataSyncId after a channel switch. InnerTubeX sends dataSyncId as `onBehalfOfUser` on login-supported requests, including `account_menu`, while omitting it from `accounts_list`. Burrata's active-page capture is Linux-only; its other platform paths still source visitorData and authUser from the `ytcfg` parsed from a native HTTP bootstrap response. Neither context-source path has been live-qualified against YouTube.

Burrata's non-Linux bootstrap path extracts optional `DATASYNC_ID` from fetched HTML `ytcfg`, truncates it at `||`, validates its bounded character set, and persists it in the YouTube session. Linux begins with the active-page capture described below and reconciles that value with fetched config. Older stored sessions without dataSyncId remain readable. The provider sends it as `onBehalfOfUser` for `account_menu` and subsequent requests, while `accounts_list` omits it; older sessions without dataSyncId retain the selected-brand-page-ID fallback. The worker validates stored and outgoing context shapes. Burrata still resolves an active handle to a stable channel ID before accepting identity, a stronger confirmation gate than the inspected Meld login screen's account-header persistence.

On Linux, Burrata now captures only visitorData, dataSyncId, SESSION_INDEX, and optional LOGGED_IN from the owned Music WebView's `window.yt.config_` through WebKit's JavaScript callback. The capture checks the dedicated login-window label and exact Music origin, enforces a two-second deadline and generation cancellation, and sends no cookies or page/account text through the callback. Native bootstrap uses that initial context; a different SESSION_INDEX or dataSyncId fails account confirmation, while visitorData may refresh from fetched ytcfg without rejection. Other platforms still use the prior HTTP-config bootstrap path, and are not qualified for active-page capture.

Linux Spotify and YouTube login windows use separate 0700 app-owned WebKitGTK data directories with incognito disabled. The pinned local Wry implementation creates a persistent WebKit data manager for each distinct directory; its own builder docs state that incognito mode ignores the WebContext. This establishes structural profile separation and persistence before confirmation. It is not a live restart/recovery test: successful confirmation clears browser data and stores the confirmed session in the OS keyring. Runtime behavior and credential recovery across restarts still need a Linux integration test. macOS and Windows remain on their existing ephemeral paths.

Burrata computes up to three separate proofs: generic `SAPISIDHASH` from SAPISID (falling back to 3PAPISID), `SAPISID1PHASH` from 1PAPISID, and `SAPISID3PHASH` from 3PAPISID. Meld's pinned dependency instead picks one cookie value by a fixed precedence and emits a single `SAPISIDHASH`. Both use timestamp + cookie value + request origin as the SHA-1 preimage; Burrata's distinct scheme labels and simultaneous proof set are an implementation difference, not a proof of improved compatibility. Burrata's collector/worker allowlists cookie names and verifies proof material against the exact handoff; Meld's login code transfers the full Music-origin CookieManager string and InnerTubeX sanitizes it. Neither source establishes that the other cookie policy is required by YouTube.

These comparisons describe private YouTube/InnerTube techniques. They are subject to upstream changes and do not imply a supported API contract. No live YouTube request was made for this review.
