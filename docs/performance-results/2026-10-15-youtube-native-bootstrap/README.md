# Native YouTube bootstrap investigation

The user signed into the main app-owned YouTube window and explicitly asked the agent to handle verification through MCP. The window and original app remain open. No account has been confirmed, no credential values were returned/logged, and no remote playlist changes occurred.

The initial generic error was narrowed to bootstrap config. An independent public fetch reproduced the problem: a minimal HTTP user agent received a 2012-byte deprecated-browser page, while the tested desktop user agent received 657467 bytes containing configuration. The worker now supplies that user agent. Numeric client IDs and symbolic request-context names are kept separate.

Subsequent account checks reached the API but found no verified identity. The source-backed channel-switcher fields, Music account-menu route, and correct authorization scheme per cookie family retained the identity guards. The bounded structural inspection returned menu renderer names only; it did not inspect account text or cookie values. See `diagnostic-observations.json`. The no-loggedOut flag is inconclusive, not proof of authentication.

The collector fix preserves the same three allowed authentication-cookie variants and generates independent matching authorization proofs, without broadening to other Google cookies or ordinary browser profiles. A connection remains unqualified until a fresh selected identity and stable channel/account ID are verified, then ordinary reads succeed. Writeback qualification is separate.

Primary implementation references: [ytmusicapi account menu at reviewed revision](https://github.com/sigma67/ytmusicapi/blob/6a671182b3ddf606b4253e2780709c52e7a1c61b/ytmusicapi/mixins/library.py), [YouTube.js account manager](https://github.com/LuanRT/YouTube.js/blob/main/src/core/managers/AccountManager.ts), and installed yt-dlp `2026.08.19` / source revision `594bd50c2c78ac432f81600d309fdc4e0a92d82c` (`yt_dlp/extractor/youtube/_base.py`, authorization helpers). The YouTube.js link is mutable; it is source evidence for the reviewed request, not a pinned deployment guarantee.

The corrected three-proof-cookie build was checked after fresh interactive sign-in. The bounded HTTP bootstrap reported `LOGGED_IN=false`; the API still returned no selected account. This is direct evidence that the transferred context was not being recognized as signed in, rather than a reason to weaken account selection. The follow-up preserves the known YouTube authentication/session cookie context used by native clients, rejects unknown cookie names, and retains every secret-output check. See [Meld comparison](meld-followup.md). The isolated YouTube login profile is becoming persistent on Linux so development restarts retain unfinished sign-in; Spotify and macOS private-window behavior remain unchanged. Live success is still unproven.
