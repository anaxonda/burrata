Current `SpotifyYouTubeMapper` creates the query from the first Spotify artist plus title, searches YouTube Music in incognito mode, flattens `SongItem` results, and compares the first candidate artist, title, and duration. `SpotifyMapper` uses normalized bigram Dice similarity: title 45%, artist 35%, duration 20%. A missing candidate duration or nonpositive Spotify duration gets a neutral duration score of 0.5. Otherwise duration contributes 1.0 within 2 seconds, 0.8 within 5, 0.5 within 10, 0.2 within 30, and 0 beyond 30 seconds. Normalization removes feature/ft parentheticals, bracket text, remaster/remix parentheticals, and punctuation. The automatic acceptance floor is 0.35. Ranking applies a separate penalty of 0.15 per extra whole-word live/video/karaoke/cover/instrumental/speed marker, capped at 0.30; an adjusted score of at least 0.95 exits early, while acceptance checks the unadjusted score. There is no hard duration rejection or complete version-identity gate in this path. This intentionally raises recall, but permits serious mismatches when title/artist dominate—particularly when input duration is absent. For example, perfect title+artist similarity with a missing input duration scores 0.90; an exact title/artist candidate more than 30 seconds off still scores 0.80, both above the 0.35 floor. Exact source links above expose these implementation details.

Successful matches are persisted in Room by Spotify ID and mirrored in a process-wide 512-entry LRU keyed by Spotify ID. The entity stores YouTube ID/title/first artist, score, timestamp and a manual-override bit. A DB hit returns immediately; the inspected mapper does not re-run source identity/duration validation on cached automatic or manual IDs. A failed search/no match returns null and is not written as a negative cache entry, so a later call repeats search. The source code has no explicit single-flight gate or caller/run token in this mapper; suspending coroutine cancellation is the available cancellation mechanism. This contrasts with Burrata's bounded per-key gates, caller-aware cancellation, expiry handling and post-extraction revalidation.

Meld's manual override path records the user-selected YouTube ID/title/artist as score 1 and `isManualOverride=true`, then the normal resolver returns the cached mapping before search. The UI presents a YouTube match dialog and, on confirm, replaces the currently playing item when applicable. This is product-level correction power, but the override is not a durable identity proof and the cache-hit path does not validate it against the original Spotify recording before use. Risk is user-selected covers, live versions or same-title tracks becoming sticky.

Meld's queue `triggerPreCache` is an optional offline audio pre-cache for a configurable number of queued tracks, disabled at count zero, optionally Wi-Fi-only, skipping local/already-cached items, and cancelling/replacing the previous pre-cache job when triggered again. It writes whole streams through `CacheWriter` to the player cache, checks coroutine cancellation between tracks, and cancels the writer when the coroutine is cancelled. A separate `SpotifyPreloadViewModel` explicitly fetches all Spotify playlists and liked songs and sequentially resolves each track into the match cache; it has a user cancel action and checks a cancel flag between pages/tracks. Neither is the same bounded, owner-scoped one-upcoming-item search preparation implemented in Burrata. The README's recommendation-queue construction is separate again from Spotify-to-YouTube identity mapping.

The previous source investigation documents Spotify token/data acquisition and YouTube InnerTube playback boundaries, but does not establish stable/public APIs. Meld's playback internals use YouTube's undocumented InnerTube path; its README and release notes are not evidence that private interfaces are stable. Source references and boundaries are recorded in [meld-session-investigation.md](meld-session-investigation.md) and [the Qobuz investigation](performance-results/2026-10-16-meld-qobuz-source/README.md).

## What Burrata currently does

Burrata keeps candidate retrieval separate from final recording acceptance. `matching.rs` computes evidence scores from title tokens (40%), artist-token overlap (30%), requested version (20%), and duration (10%), with a small official-channel bonus. The score is explicitly an evidence score rather than a match probability. “High” additionally requires exact normalized title and artist phrase coverage, verified requested version, and a duration inside the tight duration tolerance. Unknown duration/version produces review evidence, not an automatic identity claim. Known conflicting edition markers or very large duration deltas force low confidence. The final playback gates are stricter and provider-aware: YouTube/SoundCloud candidates are rechecked against extracted metadata; Monochrome's catalog path can rely on exact catalog title, structured credit identity, requested version and matching full recording duration. Unknown duration only has a narrow exception for a Monochrome catalog recording with no requested version. See [matching.rs](../src-tauri/src/matching.rs), [source_fallback.rs](../src-tauri/src/source_fallback.rs), and the explicit policy tests near the `500 Miles` fixture in [monochrome.rs](../src-tauri/src/monochrome.rs).

Search results are not durable verified mappings. Burrata keeps bounded expiring candidate, raw-search, inspection and preview-URL caches, each with keyed async gates and caller-aware cancellation. Resolved stable provider IDs are persisted separately only after extraction and identity checks; signed/expiring stream URLs are not persisted. Fingerprints invalidate mappings after recording identity changes. A cached mapping is re-extracted and revalidated before use. See [playback-cache-audit.md](playback-cache-audit.md) and the implementation in `acquisition.rs` and `playback_sources.rs`.

The foreground resolver limits each provider to two candidates, applies one shared deadline and cancellation context, and checks final identity after extraction. Upcoming-search preparation is deliberately narrow: it prepares search candidates for the next queue item, separately from ordinary preview caches, and remains cancellable/owner-bound. Native playback can prepare one next item, but this is not equivalent to downloading a configurable multi-track offline cache. Details and open qualification limits are in [playback-performance.md](playback-performance.md) and [native-playback.md](native-playback.md).

The important architectural difference from Meld's documented manual override is that Burrata has explicit source browsing/selection and reviewed, token-scoped writeback matching, but its automatic playback failure can still end in a generic “No available source matched the requested recording and version” notice. Writeback candidate selection is user-reviewed and does not mutate local tags or become an automatic provider mapping; see [writeback-recording-matching.md](writeback-recording-matching.md). A playback source selection/preview affordance is safer to borrow than Meld's unconditional “permanent override”: a user can make a mistaken selection, so the selected stable ID should still be re-extracted and checked for availability, provider identity and obvious version conflict. If user intent is to force a source despite a conflicting duration or edition, require an explicit, reversible “play anyway” action and keep it distinct from verified recording identity.

## Focused case: 500 Miles

The retained Monochrome fixture has the exact catalog title `500 Miles`, structured artist `Peter, Paul and Mary`, ISRC `USWB16500047`, and catalog duration 162.933 seconds. Burrata's request uses `Peter, Paul & Mary`, title `500 Miles`, and duration 162 seconds. The provider has an authoritative catalog identity and the only artist discrepancy is the conjunction spelling. The focused regression promotes that exact candidate and verifies it remains playable through the strict final matcher. It also rejects a different artist-credit string, a duration shifted by about 20 seconds, and an `Extended Mix` request against the unversioned candidate. This is a bounded, low-risk equivalence: for a single structured artist name, normalize `&` and `and`; do not split commas or reinterpret arbitrary `feat.` strings as equivalent credits. The change is covered by the exact fixture in `monochrome.rs` and the current provider-specific matcher. It is not evidence that broad fuzzy artist matching should be relaxed.

## Focused chart cases: missing duration

The retained Shazam chart imports for `BbY WOW` (KAROL G, Judeline & rusowsky) and `BAD TIMES` (Imael Angel) have `durationSeconds: null` and no ISRC. For `BbY WOW`, bounded general YouTube search returned candidates with differing durations, including a 226-second candidate with unknown permission. For `BAD TIMES`, general search also returned misleading same-title/artist alternatives (including 552- and 288-second results), so those results alone cannot establish the recording. New public-source evidence changes the case: `.cache/bad-times-public-identity.json` records the exact YouTube Music item `Hqp8vxkPrI8`, title `BAD TIMES`, duration 168 seconds, artist fields `Imael Angel` (duplicated identically), album `BAD TIMES`, and a verified `Imael Angel` channel with valid channel ID `UCDP7N8hTTdy-LEXvDdi-2RQ`. This establishes a structured exact source candidate for the chart item, not playback acceptance. The chart metadata and the other descriptive/general-search alternatives remain insufficient identity evidence. Earlier retained files include `.cache/bby-wow-track-private.json`, `.cache/bby-wow-youtube-private.json`, `.cache/bby-wow-inspected-private.json`, `.cache/bad-times-track-private.json`, and `.cache/bad-times-candidates-private.json`.

The safe policy for this gap is a narrow, fresh-evidence exception, not a general relaxation: with no catalog duration, permit only an exact full artist/title candidate after fresh extraction verifies the provider's verified-channel badge and valid channel ID, exact full channel name or first explicit artist credit, exact provider ID/title, complete structured track/artist identity (deduplicating repeated identical artist entries), and full duration greater than 30 seconds. Reject chapter/range excerpts and any version conflict. Search-result metadata and provisional-candidate markers only retrieve a possible source; neither can substitute for fresh verification. A bounded supplemental YouTube Music lookup is planned only after general YouTube search yields no eligible candidate: one canonical query, at most 10 results, an 8-second request cap within the shared 20-second deadline, cancellation, and no yt-dlp/helper fallback. It may nominate one distinct exact structured catalog locator for ordinary fresh extraction; it must not populate verification fields or write a duration into the chart track. The exact `BAD TIMES` Music item can qualify only if fresh extraction and the strict final checks agree; the public metadata alone does not prove it will play. General same-title uploads and arbitrary unverified sources remain blocked. The guarded implementation now passes the complete native suite (1,108 passed, 21 ignored) and fresh native playback/paused-seek checks for both reported imports. See the [runtime evidence](performance-results/2026-10-18-playback-matching/README.md); WebView qualification is tracked separately.

The product weakness is the generic no-match message: users cannot tell whether duration/recording identifiers were absent or candidates were withheld for review. Improve the message based on actual gate evidence (“No verified match; imported track has no duration or recording ID, and available candidates could not be verified”) and keep the existing explicit candidate review/preview and source-open actions available. Keep candidate duration visible and permission/availability separate. Never imply a candidate is correct because its title/artist or uploader branding looks right.

Related failures reinforce the guardrails. The retained Kaval Sviri diagnostic finds an exact title and near duration, but YouTube credits a different choir; its extractor rejects that artist conflict. The Kaufman album diagnostic evaluated 184 candidates with no accepted canonical/verified-alias, Topic, or provisional identity predicate; all 19 tracks remained unavailable, but this does not prove no source exists. See [Kaval Sviri diagnosis](performance-results/2026-10-16-youtube-channel-identity/choir-playback-readonly-diagnosis.md) and [Kaufman candidate-gate report](performance-results/2026-10-17-candidate-gate-rows/README.md). Both argue against interpreting fuzzy score or a raw five-second duration comparison as causal acceptance evidence.

## Safe ideas to borrow and heuristic risks

1. **Persistent user correction, but as a reviewed preference.** Meld's documented manual YouTube-link override addresses the “wrong result” path and lets the user recover when automatic matching cannot choose. Burrata could make an explicit per-recording “Use this source for this track” action reachable from the failed playback/source review, after a preview. Store only a canonical stable provider ID and the exact local recording fingerprint; invalidate when that fingerprint changes. On reuse, check the source again and revalidate extracted title/artist/version/duration. Make the override easy to clear and show which source is pinned. This preserves user control without equating a saved choice with verified identity. Risk: a user can deliberately select a cover, live version, or unrelated same-title upload; a permanent silent override can fossilize that error.

2. **Explain missing evidence and let the user inspect a candidate.** The two chart examples lack duration/ISRC, while their search candidates have inconsistent runtimes. Label those fields as unavailable and explain why automatic playback stopped. Provide a bounded candidate list with duration/version/uploader/permission facts and a manual preview. Do not display a fuzzy score as a probability. Risk: a user may treat the first row or “official” badge as proof, so the UI should say “candidate” and preserve explicit confirmation.

3. **Cache stable matches, not ephemeral media URLs.** Meld advertises local cached Spotify→YouTube matches for faster subsequent starts. Burrata already has a stronger split: stable verified recording→provider-ID mappings with fingerprint invalidation, while signed stream URLs get a short expiry-aware in-memory cache. Retain that split. A user override can use the same stable-ID storage shape only after preview/confirmation, tagged as user-selected rather than automatically verified. Risk: the source may disappear or change; never assume a past URL or source permission remains valid.

4. **Prepare one upcoming item, then measure.** Meld's release notes describe configurable N-item precaching (3/5/10/20) and its README describes queue generation after Spotify track selection. Burrata's one-upcoming-item preparation is a safer default for a desktop client with bounded storage and explicit cancellation. Preserve the single shared deadline, per-item owner, and no user-visible playback mutation. Increase depth only after measuring cold/warm startup, network bytes, cancellation latency, memory/disk use, and failure recovery on the supported platforms. Risk: larger speculative batches waste bandwidth/storage, compete with current playback, and can continue after a queue change unless ownership is exact.

5. **Never import fuzzy-match semantics as identity rules.** Meld's README calls its mapping fuzzy title/artist/duration matching; its current source also has a low score floor and no hard duration/version gate. Applying broad normalization (remove all parentheticals, equate all join phrases, use uploader names as artist, or accept a durationless title match) would admit covers, remixes, live takes and same-title tracks. Burrata's provider-specific exact gates and post-extraction recheck remain important. A no-duration exception should require fresh provider/channel identity plus exact title and full artist credit, matching provider ID, adequate full-track duration, and no range/chapter/version conflict; keep candidate ranking separate from this acceptance policy.
