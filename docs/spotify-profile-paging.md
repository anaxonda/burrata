# Spotify public-profile playlist paging

The current V5 source implements progressive offset/limit public-profile paging through the native Spotify read worker. Its cursor advances by the requested source-slot span (`offset + limit`), even when a page returns fewer rows. A synthetic worker regression models an omitted source slot and expects this behavior; it is an implementation assumption, not independent proof of Spotify's offset semantics. Live pages report varying row counts and totals. The current-main read sequence retained 99 distinct rows while reporting a maximum total of 110; the browse remained incomplete. The difference is unexplained, and this evidence does not establish either access to all 110 playlists or that any specific missing rows are unavailable.

## Source evidence

Pinned retained public-client artifact: `/tmp/burrata-spotify-webplayer.js`, SHA-256 `1b9dcc42aeb9c4a7abfc673da946478b100d9fb62acb8bf7f27aa63ef8769602` (the same pinned WebPlayer bundle identified in the repository executor header; retained 2026-10-15). Its user-profile client constructs `GET https://spclient.wg.spotify.com/user-profile-view/v3/profile/{encoded-user}/playlists` with `offset` and `limit`, requests `Accept: application/x-protobuf`, reads an `ArrayBuffer`, and decodes the response as the profile playlists page. The response schema visible in that bundle is:

- Paged response: field 1 = repeated playlist message; field 2 = `int32 totalPublicPlaylistsCount`. The exact paged helper decodes with codec `v`, which delegates playlist rows to codec `b` in the retained client module. The separate full-profile codec uses different fields and does not describe this endpoint.
- Playlist: field 1 `uri` string; field 2 `name` string; field 3 `imageUrl` string; field 4 `followersCount` int32; field 5 `ownerName` string; field 6 `ownerUri` string; field 7 `isFollowing` bool.

The existing profile-summary endpoint (`/profile/{user}?playlist_limit=...`) has no offset parameter. The official paged method is distinct. The staged parser is independently written; it does not copy generated Spotify decoder/client code. Treat Spotify’s bundle and endpoint as private client implementation details subject to Spotify’s terms; retain only the necessary source attribution and observed protocol contract in project notes.

## Limits and behavior

- Only the exact HTTPS profile playlist path and canonical `offset`/`limit` query are allowlisted.
- Response body is capped at 2 MiB in the worker transport and parser. Varints are limited to ten bytes and checked before numeric conversion; string decoding is fatal UTF-8; length and nesting bounds are enforced; unknown protobuf wire types 0, 1, 2, 3/4 groups, and 5 are skipped with bounds checks. Group child and end tags must use valid protobuf field numbers and matching group IDs. An empty zero-byte page correctly means total 0 because protobuf omits default-valued scalars.
- Pages are capped at 200 transport items and caller page size at 50. Manual offsets are bounded to 10,000,000; provider totals remain the protobuf int32 value. Results are marked incomplete/truncated when page counts or totals disagree, when paging ends below a positive reported total, or when the safe offset bound is reached before that total. Ordinary manual browsing is not capped at the collection action limit.
- `sp-profile-v5` cursors bind the requested next offset, maximum reported total observed so far, owner hash, signed-in account hash, 24-hour expiry, the preceding page's offset/count/requested limit, a hash of every ID in that page, its last reported total, and an inconsistency flag. A continuation refetches the preceding source window using its original requested limit and compares the returned count and ordered ID hash, then fetches the requested window. This takes at most two profile calls and supports caller page sizes up to 50. V1–V4 cursors return a refresh-required error.
- Count differences and overlap with the prior page mark the browse incomplete rather than discarding otherwise valid rows. V5 advances by the requested page span, not by the number of rows returned. The regression at `scripts/provider-session-worker.test.mjs:1034` models slot 75 as omitted from a 30-slot window and expects the following request at offset 90. That test documents the intended source-slot interpretation; it does not establish Spotify's contract independently. The maximum reported total observed is retained as `totalCount`, not treated as authoritative when page totals or returned counts disagree. When no positive total is known but rows exist, `totalCount` is `null`. An empty protobuf-default page can represent a truly empty profile; an empty page below a known positive total remains incomplete. The UI accumulates rows and deduplicates IDs across pages.

## Validation

Adapter/worker fixtures cover sparse source-slot windows, varying totals, offset 10002, caller limit 50, empty default-zero pages, unknown totals with rows, overlap/incomplete behavior, prior-page hash and cursor binding, legacy cursor reset, binary HTTP errors and retry-after diagnostics, strict protobuf parsing, and a status-200 unknown-MIME empty terminal accepted only after a verified continuation. Initial/anchor unknown-MIME empties, JSON/text empties, and non-200 empty responses remain rejected. These are synthetic fixtures; they do not qualify the provider's interpretation of offsets or reported totals.

Historical direct observations include offset 0/limit 30 returning 30 rows and total 110; offset 28/limit 2 returning 2 and total 100; offset 28/limit 30 returning 30 and total 110; offsets 58 and 60 with limit 30 returning 29 and total 109; and offset 90/limit 30 returning 10 and total 90. They establish page-to-page count variation, not why it occurs. A retained V4 API/UI run returned 30+30+29+11+0 rows, 99 unique IDs with one duplicate, then no cursor; it remained incomplete/truncated. A separate protected UI run reached 99 visible profile rows after four Load more actions, with no remaining Load more button. The maximum total 110 remains unverified; the gap between 99 retained unique IDs and 110 reported is unexplained. No evidence here establishes hidden or unavailable entries. See [historical V4 terminal API evidence](performance-results/2026-10-16-youtube-channel-identity/spotify-profile-8152-terminal-partial.json), [historical UI proof](performance-results/2026-10-16-youtube-channel-identity/protected-profile-ui-counts.json), and the [current-main five-page read](performance-results/2026-10-17-native-provider-main/spotify-profile-current-read.json).

## Scalability and consistency boundary

The retained official WebPlayer bundle shows a paged helper sending `offset` and `limit` to the profile-playlists endpoint, but exposes no snapshot ID, revision, or continuation token. V5 therefore refetches the preceding requested window and binds account, owner, expiry, and that window's ordered ID hash. This is progressive browsing, not an atomic snapshot: membership or ordering changes elsewhere may go undetected, and the maximum reported count may be stale or page-specific. The UI deduplicates playlist IDs across pages. The worker emits `snapshotConsistency: "progressive"`; neither the historical V4 99-row run nor the current-main read converts this into atomic or complete-profile browsing.

Manual offsets are safe-bounded at 10,000,000, independent of the 10,000 collection action limit. Collection-action and fresh writeback snapshot limits are unchanged. Browsing beyond the first page is accepted only for the bounded 99-result profile checks above; other profiles, larger scales, mutation races and access to every reported item remain unqualified.

V1–V4 profile cursors return a reset-required result instead of silently performing cursor migration. The integrated Rust failure mapping recognizes `CURSOR_RESET_REQUIRED` and supplies a sanitized refresh instruction. The independent complete fresh playlist snapshot and mutation preflight before every writeback remain unchanged.
